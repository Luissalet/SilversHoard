# Rival scouting before a rematch

**Scout a rematch** on an ordinary finished classic or real-time battle proposes a replacement team for the selected rival. The existing rival keeps its identity, portrait, dialogue and AI. The proposal opens in the ordinary visual TeamBuilder; accepting that editor prepares a local draft. **Save rival's team** changes only a saved trainer's team. **Save and play rematch** saves it and starts the next battle through the existing handlers. Direct seats instead offer **Play with this draft**, creating a battle without creating a saved trainer. Canceling the editor does not change trainers or create a battle. The ordinary Rematch action remains available.

`rival_scout` is shared by UI, REST and native MCP. Give a finished battle `id`, the `rival_side` (`p1` or `p2`) and optional `size` (0 retains the current rival's team size, up to six and the format limit). It returns an ordinary background job. `job_get` supplies progress and the result; `job_cancel` cancels pending work. When both seats have distinct trainer IDs, the history includes all finished encounters of that pair, including reversed seats and renamed trainers. Matching display names never identifies a rivalry. For direct seats, `encounters=[{id, rival_side}]` explicitly selects additional finished encounters and their orientation; the UI offers the same selection from paginated history. An active battle cannot be an observation source.

## What the rival remembers

The source is the existing persisted battle history, not another memory table. New individually played classic battles keep a compact species-only `replay.scouting` projection from the spectator log before the match closes. Individual watched battles supply the same projection from their actual engine run. Public protocol details from preview, switch, drag, replacement and visible form changes count; nicknames, private teams, pending choices and AI notes do not. Private/public split blocks use the public line. The original omniscient log, input record, summaries and commentary remain intact.

Older classic records use only explicit `poke` lines when a team-preview event is present. A flattened older omniscient log has no retained public/private contract; its switch lines are conservatively omitted. This does not assert that every old switch reveals a hidden species: in the current simulator an Illusion switch can retain the disguise even in the omniscient log. In the real-engine regression, the actual Zoroark is remembered as the publicly shown Pikachu until revealed. Missing evidence stays missing.

Real-time summaries already keep each member's deployment count. Only members with `switches > 0` count, using their recorded species and side without matching trainer names or Pokémon nicknames. Benched and legacy members without that counter are omitted. Real-time uses its existing public species presentation, including visible Mega forms; it does not implement the classic Illusion disguise. All observations are labelled partial. Deleting the source battles removes that memory; there is no hidden retained copy. Editing a trainer today does not rewrite species observed in an older battle.

## How a proposal is chosen

The existing usage provider supplies up to sixty popular species for the battle's format. Each candidate is built through `team_popular_sets(save=False)`, including its existing Mega normalization, written sets or usage fallback and source-format metadata. A deterministic greedy ranking uses the generation's actual type chart and the damaging moves of those returned sets. Each step prefers covering previously uncovered observed species, then additional type effectiveness, resistance to the observed species' types, usage and canonical name. Members sharing a base species are not repeated.

The whole selected team is checked by the ordinary format validator with the battle's rules and level rules. Missing observations, disabled popular sets, too few candidates or a failed final validation produce an unavailable proposal and preserve the previous team. No incomplete or illegal roster is presented as ready. Provider failures are reported by the existing job/error mechanism. A proposal does not guarantee the strongest legal alternative: the selector does not search every combination after a failed validation.

The reasons describe type coverage of the original proposed sets. After editing, they remain provenance for that original proposal, not a new analysis of the edited draft. The team is validated again when the edited draft is accepted and before saving or starting. Coverage does not account for abilities, items, accuracy, speed, current battle state or tactical sequencing and does not predict a win rate. There is no additional LLM, opponent persona, simulator, server or battle rule.
